## Review Summary: Request Changes

This PR does not do what the description claims, and the single file it adds is a non-compiling placeholder committed to a path this project does not use. Recommend **do not merge** in its current state.

### Critical issues

**1. Wrong path — the file is unreachable dead code.**
The PR adds `src/components/dashboard/CommandCentre.tsx`, but this repo has no `src/` directory. The real component lives at `components/dashboard/CommandCentre.tsx` (11,241 lines), and `tsconfig.json` maps `@/*` → `./*` (project root), not `./src/*`. Nothing imports the new file, so it changes zero runtime behavior and creates a confusing duplicate.

**2. Nothing is actually refactored.**
The description says "Refactored monolithic CommandCentre.tsx," but the diff is `+81 / -0` on a brand-new file. The existing 11k-line component is untouched, so the stated goal (breaking up the monolith) is not accomplished.

**3. The code does not compile.**
`export type CommandPage = 'briefing' | 'signals' | /* other pages */;` is invalid TypeScript — a union ending in `|` followed by a comment. This alone fails typecheck/build. The real component already exports a complete `CommandPage` union of ~30 page IDs.

**4. It is a skeleton, not an implementation.**
The file contains literal placeholder comments committed as source:
- `// ... (imports abbreviated for token limit)`
- `BriefingRoom` body is `// ... existing code` — an empty stub, despite the claim "Added full BriefingRoom component with confidence visualization."

**5. `BriefingRoom` already exists.**
The real `BriefingRoom` is a `React.memo` component (line ~356 of the existing file) that computes confidence lanes via `buildConfidenceLanes` / `computeOverallConfidence` and fetches an AI briefing with an `AbortController`. This PR re-declares it as an empty stub.

**6. The "Supabase optimization" is fake and would regress behavior.**
The `useEffect` does not call Supabase — the query is a comment and data is faked with `setTimeout(..., 400)` reading from `props.signals`. Realtime signals are already handled by the dedicated `useDashboardSignalsRealtime` hook. Wiring this in would remove working realtime behavior.

### Secondary issues
- Pervasive `any` (`props: any`, `s: any`, `BriefingRoom(...: any)`) defeats type safety.
- Hardcoded colors (`bg-zinc-950`, `text-white`, `text-emerald-400`) instead of the design-system tokens the description claims to use.
- Several imports (`useCallback`, `useMemo`, `dynamic`, various types) are unused in the stub.

### Suggested path forward
1. Delete the `src/...` file; target the real `components/dashboard/CommandCentre.tsx`.
2. If splitting the monolith, extract the actual `BriefingRoom` and `SignalsPage` into `components/dashboard/pages/` (following the existing `./pages/*` pattern), importing shared types from `@/lib/dashboard/*` rather than re-implementing them.
3. Keep `useDashboardSignalsRealtime` as the signals data source; do not fake it with `setTimeout`.
4. Ensure typecheck and build pass before re-requesting review.
